# 主软件自动诊断与调参实施计划

依据 [协议方案](主软件自动诊断与调参协议方案.md) 和 2026-09 的代码现状执行。以下各阶段的完成标准是可测试的交付门槛；未达标的阶段不能称为完成。

## 代码边界与兼容性

- `IAlgorithmPlugin/1.0`、`IAlgorithm`、`AlgorithmResult` 和 `Host` 的既有虚函数与字段布局保持不变；旧 DLL 无诊断字段时仍可加载、运行、显示结果。诊断档案作为参数 schema 的可选 `diagnostics` 对象，运行事实放入 `AlgorithmResult.metrics.diagnostics`。协议版本独立于参数版本。
- `FrameworkSDK` 增加纯函数校验器 `fw::Diagnostics`，由 `Runtime` 在插件加载与结果交付前调用。无档案或不兼容版本只关闭专有诊断；不阻断正常算法。无效运行报告从正式展示中剔除并记录错误。
- `Runtime::startTrial` 是主软件内部接口，完成后只发 `trialFinished`，不发普通 `Host::finished`。主界面只在普通 `finished` 中写正式数据列表。试跑在同一输入及参数快照上顺序执行，保持已有单 worker 约束。取消沿用 `stop()`。
- `MainUI` 提供问题清单和试跑对比会话，采用/恢复只修改参数编辑器；不自动接受输出。不同角色、目标身份、几何位置、实测/拟合和插补标记必须保持分离。

## 1. 协议、机器校验和开发入口

文件：`docs/自动诊断协议.md`、`docs/自动诊断实施计划.md`、`schemas/diagnostics-*.schema.json`、`sdk/include/fw/Diagnostics.h`、`sdk/src/Diagnostics.cpp`、`AGENTS.md`、`docs/算法开发.md`、`examples/algorithm-template/*`、`tests/FrameworkTests.cpp`。

完成标准：声明和报告的必填字段、稳定代码、阶段、区域、目标身份、可观测性、证据口径及大小/数值限制都有机器校验；测试覆盖缺字段、非法数值、未知代码和版本冲突。旧测试插件无需修改，加载和运行仍通过。

## 2. 主软件通用诊断接收与展示

文件：`core/Runtime.*`、`plugins/main/MainUI.cpp`、`tests/FrameworkTests.cpp`。

完成标准：有效报告按严重程度、阶段、区域和目标显示；无报告提示“未提供结构化诊断”；无效报告不能被当成可信事实；算法失败与成功但局部警告分开。输入不合格或 `validate()` 只有文字时展示原文，不猜诊断代码。

## 3. 试跑隔离与有限顺序试参

文件：`core/Runtime.*`、新增 `core/TrialSession.*`、`plugins/main/MainUI.cpp`、`tests/FrameworkTests.cpp`。

完成标准：基线和单参数邻值按档案规则生成，先过参数校验，限制变体数/总耗时；试跑结果不触发正式 `finished`，不进数据列表，也不改当前参数；停止后不启动下一变体；每次保留输入、参数和诊断快照。取消、失败、超时、关闭界面均有测试。

## 4. 首个算法接入与跨区域比较

文件：`algorithms/carExtractFeature/parameters.json`、`MyAlgorithm.cpp`、`tests/*`；通用比较放在 `core/`，不写入 CAR。

完成标准：CAR 上报六阶段的稳定代码、整体及连续问题区段、支持量、原始位置；声明实测边缘/拟合轨迹两个角色及相同目标身份。对比先匹配 `targetId + role`，用原始索引或世界坐标定位共同区段，分别列出目标区域改善和其余区域退化，并检查断段和插补数量。只有当前云的内部证据时结论标“待人工确认”，数据问题和身份不明时不给数值。

## 5. 标注验收与数值推荐

文件：`core/` 建议规则与标注读取、`docs/` 标注格式与样本清单、算法回归测试。

完成标准：以工件类型/扫描方式/算法版本分组，保留不参与调参的验收工件；覆盖左右/多目标、缺测、误连、局部改善引起的其他区域退化。由用户确定误差和运行预算后，才可将通过验收的区间标为“已验证”；否则最多给试探方向或“待人工确认”。

## 当前事实与风险

- `CloudData.id` 为读入时 UUID，CAR 输出沿用其 ID 加名称；它只能关联本次输入，不能跨重新导入断言同一工件。CAR 的 `section_id` 是本次恢复的几何截面编号，跨参数运行只能与物理位置或原始点索引联合对齐。
- 当前 Runtime 的 `start()` 只检查第一份云的字段，CAR 自身要求恰好一份保留点序的云；主软件不能从 XYZ 自动确认采集顺序与特征存在性。
- 旧插件元数据还要匹配 `FW_BUILD_ID`。这不是任意历史 DLL 的跨构建兼容承诺；兼容验收使用同构建的无诊断插件。

## 2026-09-18 实施状态

- 阶段 1 已完成第一版：协议文档、JSON Schema、SDK 机器校验、算法模板、AI 开发阅读规则及 CAR 档案均在源码中。宿主对无效档案/报告降级，保留旧插件正常运行。JSON Schema 是交换格式说明；跨字段一致性（ID、版本、参数快照、输出点数等）由 C++ 校验器执行。
- 阶段 2 已完成基础接收和问题清单：显示严重程度、最早阶段、目标、位置、异常来源和证据详情；点击局部问题可在点云上标出代表点或包围盒。原始点索引和连续曲线段的精确选区高亮、整云采样体检尚未完成。
- 阶段 3 已完成最多四个单参数邻值的顺序试跑、单次 30 秒/整会话 120 秒界限、取消、正式结果隔离、条件式一键采用/恢复参数和轻量诊断对比。可能抹掉真实瑕疵的参数禁止一键采用；未判明异常消失或输出统计变化也触发人工复核。比较当前只列出按目标/角色/来源索引匹配的问题条目及输出统计变化；尚未完成空间曲线偏差、覆盖区段、错误连接拓扑及局部退化的独立几何判据。因此试参列表仅为人工复核，不能自动推荐“最佳”数值。超时通过取消协作实现；若第三方算法不检查取消，宿主仍需等待其返回。
- 阶段 4 已接入 CAR 首例：相邻截面拒绝问题合并成区域事件，实测/拟合身份分离，包含插补与段数统计。来源统一为 `undetermined`；所有 CAR 试参声明为可能掩盖真实瑕疵，因此允许隔离试跑供对比，但一键采用被禁止，需人工复核后手动设置。系统不把真实物理缺陷归类为算法错误，也不会因平滑后异常消失就宣称改善。其他算法尚未接入。
- 阶段 5 未开始：缺少人工确认的缺陷/正确边缘标注、可观测区域定义、交付误差阈值和留出工件。已验证数值推荐暂不可用。

验证：主工程 `FrameworkTests` Release 构建及 CTest 通过，覆盖校验错误、旧插件、试跑隔离/取消、诊断列表与一键采用保护；CAR 插件构建及 `car_lap_edge_plugin` 通过；设置 `CAR_PLUGIN_PATH` 和 `CAR_SAMPLE_PATH` 后，主软件 Runtime 在真实 `3.pcd` 上加载 CAR、接受结构化报告，并经 UI 自动检查执行基线及有依据的顺序试跑，确认输出不进入正式数据列表。测试机运行时须将 Qt、PCL、VTK、FLANN、Qhull、OpenCV 的 DLL 目录放入 `PATH`；仓库当前未配置这些第三方 DLL 的自动测试部署。
